# REV-015 — LoginPage / AuthGuard / AuthContext 会话闭环 review

## 背景
前端采用 cookie-based session（由后端 `/api/auth/local/login` 设置 cookie，`/api/auth/user` 读取当前会话），并通过：
- `AuthProvider.refresh()` 启动时拉取用户态
- `AuthGuard` 对受保护路由做重定向（带 `next`）
- `ainovel:unauthorized` 全局事件处理 401
- 定时 `/api/auth/refresh` 刷新 session

本条目审计登录/刷新/401/logout 行为，并与后端 cookie 策略对齐，产出可复核结论与建议。

## 检查项
- `next` 参数安全性（防 open redirect）
- 登录成功后状态/路由跳转闭环
- 401 处理链路（refresh、refreshSession、全局 unauthorized event）
- logout 是否清理本地状态并与后端 cookie 退出对齐
- dev_fallback 的边界与风险（仅在“后端无需 auth 也可访问 projects”时启用）

## 发现点
### 1) next 参数已做最小安全约束
`LoginPage.safeNextPath` 只允许以 `/` 开头且拒绝 `//`，避免明显的 open redirect。

### 2) cookie session 闭环与后端契约一致
- 登录：`/api/auth/local/login` 成功后直接将状态置为 `authenticated`，并保存 `currentUserId`（不依赖 token 存储）。
- 刷新：启动时 `refresh()` 访问 `/api/auth/user`，成功后更新 user + session.expireAt。
- 续期：`authenticated` 状态下每 5 分钟调用 `/api/auth/refresh` 更新 expireAt；401 时切回 `unauthenticated`。
- 退出：`logout()` 调用 `/api/auth/logout`（失败忽略），清理本地 userId 后再 `refresh(silent)` 以对齐后端实际会话状态。

### 3) 401 处理策略清晰（但依赖 apiClient 触发事件）
`AuthProvider` 监听 `ainovel:unauthorized`，在已认证态收到 401 时切换为 `unauthenticated`，由 `AuthGuard` 负责重定向到登录页。

### 4) dev_fallback 行为有明确触发条件
当 `/api/auth/user` 返回 401，但 `/api/projects` 仍可访问时进入 `dev_fallback`，允许本地开发继续使用（AuthGuard 不拦截）。
在正常“需要登录”的环境下，`/api/projects` 也会 401，因此不会误入 dev_fallback。

## 结论
当前前后端会话闭环与 cookie 策略一致，路由守卫与 401 处理链路清晰，且相关契约/UI 测试覆盖通过；无需代码改动。

## 修复/改进建议（不在本次实现范围内）
- 若未来出现 “dev_fallback 误触发” 的风险，可考虑增加更明确的环境开关（例如仅在 `DEV`/`VITE_*` 标志下允许）。
- 可基于 `session.expireAt` 做更精细的 refresh 调度（减少固定轮询），但属于优化项。
