# REV-007 — [security][secrets] API Key Token 脱敏与响应面审计

## 背景
- 系统支持多 Provider LLM 调用与用户配置 API Key；需要确保：
  - 服务端日志永不输出明文 key/token；
  - API 响应永不回传明文 key/token（只允许 `has_api_key` / `masked_api_key` 等脱敏字段）。

## 检查项
- 后端：密钥存储/解密/掩码函数是否安全；接口响应是否只返回脱敏字段。
- 日志：异常日志与结构化日志是否具备脱敏；httpx/httpcore 是否避免打印请求细节。
- 前端：仅在提交时发送 `api_key`，展示侧使用 `masked_api_key/has_api_key`；不在 UI/console 打印明文。

## 发现点
1) 后端响应面：LLM Profile 仅返回 `has_api_key` / `masked_api_key`
- `backend/app/api/routes/llm_profiles.py::_to_out` 输出：
  - `has_api_key=bool(api_key_ciphertext)`
  - `masked_api_key=api_key_masked`
- 未见把 `api_key_ciphertext` 或明文 key 放入响应的路径。

2) 密钥存储与掩码：支持 prod `enc:`，并提供 `mask_api_key`
- `backend/app/core/secrets.py`：
  - `encrypt_secret/decrypt_secret`：prod 强制 `enc:`（Fernet），dev 允许 DPAPI（win32）/plain 兼容但 prod 禁止。
  - `mask_api_key(...)`：仅暴露前缀 + 后 4 位。

3) 日志侧：异常 message 在 dev 下做正则脱敏；prod 不输出 message/stack
- `backend/app/core/logging.py`：
  - `_redact_secrets(...)` 覆盖 query `key/api_key/token`、`sk/rk/pk-*`、`AIza*`、`Bearer ...`、`X-LLM-API-Key`。
  - `configure_logging()` 将 `httpx/httpcore` 日志级别提升到 WARNING，降低请求细节泄露风险。

4) Provider 调用使用 Header 传 key（不出现在 URL Query）
- 代码中多处使用 `Authorization: Bearer {api_key}` / `x-api-key` / `x-goog-api-key`（符合不落 URL 的要求）。

## 证据（命令与关键输出摘要）
- 扫描：
  - `rg -n "api_key|Authorization|Bearer|X-LLM-API-Key|masked_api_key|has_api_key" backend/app frontend/src -S`
    - 命中 `mask_api_key`、`_redact_secrets`、provider headers、以及响应字段 `has_api_key/masked_api_key`
- 关键文件：
  - `backend/app/core/secrets.py`（加密/解密/掩码）
  - `backend/app/core/logging.py`（脱敏策略）
  - `backend/app/api/routes/llm_profiles.py`（响应面仅脱敏字段）

## 结论
- 未发现“响应回传明文 key/token”的问题；后端已按 `has_api_key/masked_api_key` 口径输出。
- 日志侧已有明确脱敏实现与 prod 降噪策略；符合本项要求。
