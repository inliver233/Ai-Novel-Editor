# REV-004 — [security][validation] Backend 输入校验与 fail closed 审计

## 背景
- FastAPI + Pydantic 的请求校验是“第一道防线”：应尽量做到 **fail closed**（拒绝未知字段、限制 payload 尺寸/边界），避免“悄悄忽略”导致安全/逻辑误判。
- 本项审计范围：`backend/app/schemas/*` 与 `backend/app/api/routes/*` 中的请求体/Query/Header 参数边界。

## 检查项
- 请求体（Body）：
  - 字段边界：`Field(min_length/max_length/ge/le)` 是否覆盖关键输入（尤其是大文本、JSON 字符串、prompt/markdown）。
  - `extra` 策略：是否 `extra="forbid"`（拒绝未知字段）。
  - “开放形状”字段：`dict[str, Any]` / `list[Any]` 是否存在可控上限（避免超大 JSON）。
- Query/Header：
  - `Query(..., max_length=...)`、`Header(..., max_length=...)` 是否对可控字符串加上限。

## 发现点
1) 大部分 schema 已对常见字符串/数值做了边界（good）
- 例如章节标题、指令、query_text、count/limit 等普遍存在 `max_length` / `ge/le`。

2) `extra="forbid"` 目前只在少数关键 schema 中启用（存在 fail-open 面）
- 扫描发现：`backend/app/schemas/memory_update.py` 显式使用 `ConfigDict(extra="forbid")`；
- 其余大多数请求 schema 仍是 Pydantic 默认行为（通常为 **忽略未知字段**），这在安全口径下更偏 fail-open。

3) Header 字段缺少显式长度上限（存在“超大 Header”输入面）
- 多个生成/测试相关接口通过 `Header("X-LLM-Provider" / "X-LLM-API-Key")` 读取外部输入，但未加 `max_length`。

## 本次修复（最小改动）
- 对所有 `X-LLM-Provider` / `X-LLM-API-Key` 的 Header 入参增加 `max_length`：
  - Provider：`max_length=64`
  - API Key：`max_length=4096`
- 目的：在框架层面尽早拒绝异常超大 Header，降低 DoS/异常路径风险，同时不改变正常请求兼容性。

涉及文件：
- `backend/app/api/routes/chapters.py`
- `backend/app/api/routes/chapter_analysis.py`
- `backend/app/api/routes/outline.py`
- `backend/app/api/routes/llm.py`

## 缺失边界清单（建议后续补强）
- `extra` 策略：
  - 建议引入统一的 Request 基类（例如 `RequestModel`：`ConfigDict(extra="forbid")`），并逐步将请求 schema 从 `BaseModel/ORMModel` 迁移为该基类（优先 auth/写接口）。
- “开放形状”字段：
  - 若存在 `dict[str, Any]` / 大 JSON 字符串输入（如 analysis/preset/extra），建议增加：
    - 字符串长度上限（`max_length`），或
    - 自定义 validator 对序列化后长度做 hard limit。
- Query：
  - 对可控字符串（如 `chapters`、导出相关开关）可按需要补 `max_length`（不是本次改动重点）。

## 证据（命令与关键输出摘要）

- `rg -n "Header\\(" backend/app/api/routes -S`（定位所有 Header 输入面）
