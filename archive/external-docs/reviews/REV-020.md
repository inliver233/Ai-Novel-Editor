# REV-020 — structured_memory 表设计 / 软删语义 / list_structured_memory review

## 背景
结构化记忆（structured memory）以多张表存储：entities/relations/events/foreshadows/evidence，并通过 `deleted_at` 实现软删除。
本条目审计：
- 软删语义是否一致、是否会影响唯一约束与“重新创建”
- 索引是否覆盖常见查询（按 project_id + updated_at + deleted_at）
- `GET /api/projects/{project_id}/memory/structured` 的 shape 与 limit 策略

## 检查项
- 模型字段：`project_id` 外键、`deleted_at`、`updated_at/created_at`、唯一约束
- API：`include_deleted` 与 `limit` 的边界、排序字段、返回 payload
- 性能：是否存在明显缺失的索引（尤其是 project_id + 排序字段）

## 发现点
### 1) 软删语义一致，但唯一约束与软删存在“墓碑”效应
- `MemoryEntity/Relation/Event/Foreshadow/Evidence` 均使用 `deleted_at` 标记软删。
- `MemoryEntity` 的唯一约束为 `(project_id, entity_type, name)`，不包含 `deleted_at`：
  - 软删后无法用同名同类型再次创建（除非业务层选择复用/取消删除）。
- `MemoryRelation` 同理：唯一约束不包含 `deleted_at`，软删后同 relation 无法“重建为新行”。

这属于设计选择：**软删作为 tombstone**（避免历史冲突），但如果产品希望“删除后允许重建同名实体”，需要额外方案（见建议）。

### 2) list_structured_memory 的查询/limit 策略清晰
- `include_deleted=false` 时，对各表追加 `deleted_at IS NULL` 过滤。
- `limit`（默认 50，上限 200）会分别作用于每个列表（entities/relations/events/foreshadows/evidence），所以总返回量上限约为 `5 * limit`（另含 counts）。
- 排序：
  - entities/relations/events/foreshadows：`updated_at DESC`
  - evidence：`created_at DESC`

### 3) 索引基本覆盖 project_id 过滤，但排序字段可优化（建议项）
现有索引集中在 `project_id` 与部分业务字段（如 relations 的 from/to、foreshadows.resolved）。
列表接口排序依赖 `updated_at/created_at`，若项目数据量增长明显，可考虑引入组合索引：
- `(project_id, updated_at)`（或 `(project_id, deleted_at, updated_at)`）
- `(project_id, created_at)`（evidence）

## 结论
结构化记忆表的软删字段与 API 过滤逻辑一致；当前索引足以支撑小/中规模数据的按项目列表。若产品期望“软删后可重建同名实体/关系”，需调整唯一约束策略或引入“复用/取消删除”的业务逻辑。

## 改进建议（不在本次实现范围内）
- 唯一约束与软删：
  - 方案 A：业务层在创建前尝试查找 soft-deleted 记录并“恢复”（清空 deleted_at）
  - 方案 B：使用 partial unique index（仅约束 `deleted_at IS NULL`，Postgres 更易实现；SQLite 需权衡）
- 性能：
  - 在数据量增大时，补齐 `(project_id, updated_at/created_at)` 组合索引并做 explain/基准测试。
