# REV-018 — Chroma RAG chunking / ingest / query / rebuild review

## 背景
向量检索（Vector RAG）用于从世界书/大纲/章节中构建 chunk 并检索出可注入的上下文块，要求：
- chunk/metadata/预算（max chunks / char limit）可控
- 缺少 embedding 依赖时 fail-soft（返回稳定结构而非崩溃）
- 日志可观测但不泄露隐私（不记录 query 文本、chunk 原文、密钥）

本条目审计 `vector_rag_service` 与 `/api/projects/{project_id}/vector/*` 路由，以及前端 ContextPreviewDrawer 的调试展示。

## 检查项
- chunking：`chunk_size/overlap`、不同 source 的拼接方式、metadata 字段
- query：去重策略（按 source/source_id）、预算策略（final_max_chunks/final_char_limit）、dropped 语义
- fail-soft：embedding 配置缺失时 status/query 的返回结构
- observability：日志是否仅记录“长度/计数/ID”，避免泄露 query/chunk/secrets

## 发现点
### 1) chunking 与 metadata 结构合理
- `_chunk_text`：按 `chunk_size` 切片并带 overlap；对空白做 strip，避免空 chunk。
- `build_project_chunks`：
  - `worldbook/outline`：`{title}\\n\\n{content}` 作为 chunk 来源
  - `chapter`：带 “第 N 章” header + 正文，且正文为空会跳过
  - metadata 包含 `project_id/source/source_id/title/chunk_index`，章节额外包含 `chapter_number`

### 2) query 预算 dropped 语义存在边界 bug（已修复）
`query_project` 会：
- 对候选按 `(source,source_id)` 去重（避免同一资源多 chunk 占满预算）
- 通过 `vector_final_max_chunks` 限制最终注入块数，通过 `vector_final_char_limit` 限制注入文本长度

问题：当候选中存在 duplicate_source 且达到 max_chunks 时，原实现用 `trimmed_candidates[len(final_chunks):]` 追加 `budget` dropped，
会因为 `len(final_chunks)` 并不等于“已处理候选数”而误把**已入选**的 candidate 记为 `budget` dropped（影响调试可解释性）。

修复：改为记录实际处理到的下标（`processed`），仅对“未被处理到的剩余候选”追加 `budget` dropped。

### 3) fail-soft：embedding 配置缺失时返回稳定结构
`vector_rag_status/query_project` 在缺少 `embedding_base_url/model/api_key` 时会返回：
`enabled=false + disabled_reason + candidates=[] + final(empty) + prompt_block(empty)`，满足 Phase 0 的稳定结构要求。

### 4) 日志与隐私：避免把异常文本写进日志（已加固）
成功日志仅记录 `query_chars/计数/候选 ID/耗时/filters`，不包含 query/chunk 原文，符合隐私要求。

风险点：pgvector 路径异常时原先记录 `error=str(exc)`，在部分 SQL/参数异常场景可能包含 chunk 原文或查询细节。
本次将相关日志字段改为 `error_type=<ExceptionClass>`，同时 fallback 信息中的 `error` 也改为异常类型名，降低泄露风险。
