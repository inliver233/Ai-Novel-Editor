# REV-001 — [security][auth] Cookie session CORS CSRF 审计

## 背景
- 本项目前端通过 `fetch(..., { credentials: "include" })` 携带 Cookie 会话访问后端。
- 后端启用 `CORSMiddleware(allow_credentials=True)`，并通过 Cookie 解析 `user_id` 作为会话鉴权来源。

## 检查项
- CORS：`allow_credentials` 与 `allow_origins` 的组合是否可能放大 CSRF 风险（尤其是 `*` 配置）。
- Cookie：`Secure` / `HttpOnly` / `SameSite` / `Path` / `Max-Age` 设置是否满足 prod 安全基线。
- CSRF：是否依赖 `SameSite`，是否存在“跨站可触发的写操作”。

## 发现点
1) CORS 允许携带凭证
- `backend/app/main.py` 设置 `allow_credentials=True`，`allow_origins` 来自 `settings.cors_origins_list()`（默认 `http://localhost:5173`）。  

2) 会话 Cookie 安全属性总体合理，可通过配置收紧
- `backend/app/core/auth_session.py::set_session_cookies`：
  - `httponly=True`（会话 cookie）
  - `secure = (APP_ENV == "prod")`
  - `samesite = settings.auth_cookie_samesite`（默认 `lax`，可配置 `strict/none`）
  - `path="/"`，带 `max_age`
- 另有 `session_expire_at` cookie：`httponly=False`（仅时间戳，暴露面较小，但如前端无需读取可考虑改为 `HttpOnly`）。

3) 前端默认携带 Cookie（与后端会话形态一致）
- `frontend/src/services/apiClient.ts` 默认 `credentials: "include"`。

## 证据（命令与关键输出摘要）
- `rg -n "allow_credentials|auth_cookie_samesite|set_cookie" backend/app -S`
  - `backend/app/main.py:97 allow_credentials=True`
  - `backend/app/core/config.py:45 auth_cookie_samesite="lax"`
  - `backend/app/core/auth_session.py:118/127 response.set_cookie(...)`

## 结论
- 当前实现主要依赖 `SameSite`（默认 `lax`）降低跨站 Cookie 自动携带风险；在“前后端同站（同 eTLD+1）”部署下，建议在 prod 进一步收紧为 `SameSite=strict`（仍可跨子域同站携带）。
- 最大风险来自**错误的 prod 配置**（例如把 `cors_origins="*"` 且将 `SameSite=None`），会把 Cookie 会话暴露到跨站请求面。

## 修复方案（建议）
- Prod 推荐配置（不改代码也可落地）：
  - 明确设置 `CORS_ORIGINS` 为前端实际 Origin 列表（不要使用 `*`）。
  - `AUTH_COOKIE_SAMESITE=strict`（除非确需跨站；跨站时必须 `none` 且 `secure=true`，并建议引入 CSRF token 或改为 header token）。
- 若后续确认前端不需要读取 `session_expire_at`：可将该 cookie 也设为 `HttpOnly` 以进一步收敛暴露面（需同步前端逻辑）。
