# REV-022 — GraphContext / GraphPage review

## 背景
GraphContext（Phase 6.1）基于 structured memory（entities/relations/evidence）从 `query_text` 中命中实体并做 1-hop 扩散，生成：
- nodes/edges/evidence（结构化结果）
- prompt_block.text_md（用于注入/回放）

本条目审计实体匹配、扩散与截断策略、prompt_block 体积控制，并检查 GraphPage 的 UI 渲染安全性。

## 检查项
- 实体匹配：name/aliases/aka 的命中策略与排序
- 1-hop 扩散：边选取、node 上限/edge 上限、截断语义
- prompt_block：行数限制与潜在体积风险
- UI 渲染：是否存在不安全的 HTML 注入点（XSS）

## 发现点
### 1) 实体匹配策略直观但在大项目下可能偏重
- `_match_entities` 会对每个 entity 的 `name + aliases/aka` 做 substring 匹配（lowercase），按“最早出现位置 + 更长命中优先”排序。
- 优点：实现简单、可解释。
- 风险：当项目实体数量很大时，匹配复杂度约为 `O(num_entities * num_aliases)`，且会先全量加载 entities（需要时可优化为 DB 侧预过滤/限制）。

### 2) 1-hop 扩散与截断语义明确
- hop 被 clamp 到 `0/1`（当前只支持 1-hop）。
- edges 选取：
  - 仅查询与 seed_ids 相连的 relations
  - `max_edges` 达到后 `truncated_edges=true` 并停止
  - `max_nodes` 超限时跳过该边并标记 `truncated_nodes=true`（继续扫描以尝试找到“不会引入新节点”的边）
- evidence：按 `source_id ∈ (node_ids ∪ edge_ids)` 查询，limit 200，满足基本可观测性。

### 3) prompt_block 体积控制存在基础上限（仍建议加 char budget）
- 输出仅包含：Matched、Nodes（最多 30 行）、Edges（最多 60 行），能避免无上限膨胀。
- 但每行内容长度未做 char_limit，若 name/description 很长仍可能较大（建议项）。

### 4) GraphPage 渲染安全（无 HTML 注入）
GraphPage 全部以 React 文本渲染（`<pre>`/`<div>`），未使用 `dangerouslySetInnerHTML`，因此后端返回的 `description_md/quote_md/prompt_block.text_md` 不会被当作 HTML 执行，满足基础 XSS 安全。

## 结论
当前 GraphContext 的 1-hop 逻辑正确且具备节点/边截断；GraphPage 的 UI 渲染方式安全。性能瓶颈主要在“全量加载 entities + 逐个 substring 匹配”，在实体规模较大时需关注。

## 改进建议（不在本次实现范围内）
- 为 prompt_block 增加 `char_limit`（超过则截断并标记 `truncated.prompt_block=true`）。
- 若实体规模变大，可增加：
  - 仅加载最近更新的前 N 个 entities，或
  - DB 侧 name/alias 索引与查询（避免全量扫描）。
