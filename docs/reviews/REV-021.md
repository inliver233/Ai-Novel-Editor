# REV-021 — MemoryUpdate v1 事务 / 幂等 / 回滚 / 越权边界 review

## 背景
MemoryUpdate v1 提供：
- `POST /api/chapters/{chapter_id}/memory/propose`：生成 change_set + items（含 before/after diff）
- `POST /api/memory_change_sets/{id}/apply`：应用变更（软删/更新/创建）
- `POST /api/memory_change_sets/{id}/rollback`：回滚已应用变更

本条目审计状态机、事务边界、幂等与越权边界（change_set_id 跨项目不可被滥用），并补足测试。

## 检查项
- propose：
  - `idempotency_key` 是否按 project 维度幂等
  - before/after 的生成是否与目标表一致
  - commit/rollback 边界（失败是否回滚）
- apply：
  - 仅允许 `status=proposed` 进入 apply；重复 apply 幂等
  - 逐 item 应用的事务边界（一次 commit）
  - integrity error 时是否标记 failed
- rollback：
  - 仅允许 `status=applied` 进入 rollback；重复 rollback 幂等
  - 逆序回滚 item（依赖关系更安全）
- 权限：
  - apply/rollback 是否按 change_set.project_id 做 require_project_editor 校验，防止跨项目越权

## 发现点
### 1) 状态机清晰
- propose：生成 `status=proposed`
- apply：`proposed → applied`，重复 apply 返回 `idempotent=true`
- rollback：`applied → rolled_back`，重复 rollback 返回 `idempotent=true`
- 非法状态转换返回 conflict

### 2) 事务边界：apply/rollback 以单次 commit 为原子单位
- apply：遍历 items 后设置 status/applied_at 并 `db.commit()`；异常统一 `db.rollback()`
- rollback：遍历 items（desc）后设置 status/rolled_back_at 并 `db.commit()`；异常统一 `db.rollback()`

### 3) 幂等策略：propose 以 (project_id,idempotency_key) 去重
- propose 先按 `(project_id, idempotency_key)` 查已有 change_set，有则直接返回（idempotent）。
- 若并发导致唯一约束冲突：捕获 IntegrityError 后回查并返回既有 change_set（fail-closed 且可恢复）。

### 4) 跨项目越权：路由侧按 change_set.project_id 做 editor 校验
`/apply` 与 `/rollback` 先 `db.get(MemoryChangeSet, id)`，再用 `require_project_editor(project_id=change_set.project_id)` 校验权限。
因此即使拿到其它项目的 `change_set_id`，也无法在非成员项目上 apply/rollback。

本次补充了单测验证该越权路径为 403。

## 结论
MemoryUpdate v1 的状态机/事务边界/幂等策略清晰；apply/rollback 的权限校验基于 change_set.project_id，可阻断跨项目越权。本次补齐了关键越权单测以降低回归风险。
