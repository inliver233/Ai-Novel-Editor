# ANE-0280 审计：`SecureKeyManager`（加密算法 / 密钥来源 / 错误处理）

审计对象：`src/core/secure_key_manager.py`

## 现状摘要

- **存储介质**：本地文件 `api_keys.json`（Windows: `%LOCALAPPDATA%/<app_name>/secure/api_keys.json`；其他平台：`~/.config/<app_name>/secure/api_keys.json`）。
- **加密算法**：`cryptography.fernet.Fernet`（对称加密 + 完整性校验）。
- **密钥派生**：PBKDF2-HMAC-SHA256 从“机器特征字符串”派生 32 字节 key（固定 salt：`b'ai-novel-editor-salt'`，iterations=100000）。
- **机器特征来源**：
  - Windows：`HKLM\\SOFTWARE\\Microsoft\\Cryptography\\MachineGuid`
  - macOS：`ioreg ... IOPlatformUUID`
  - Linux：`/etc/machine-id`
  - fallback：`<user_home>-<app_name>-fallback`
- **调用方**：
  - `AIConfig.api_key` 从安全存储读取；
  - `Config._migrate_api_keys` 会把旧版明文 key 迁移并清空；
  - `RAGService` 已尝试从安全存储读取（但 provider/命名仍需统一）。

## 主要问题与风险

1) **固定 salt**  
PBKDF2 使用固定 salt，会导致同一“机器特征”在不同安装之间派生出相同 key；不利于隔离与后续演进（但并不直接导致明文泄露）。

2) **“机器特征”并非秘密**  
MachineGuid / machine-id/UUID 在本机通常可被读取。若攻击者已能读取 `api_keys.json`，往往也能读取这些标识，从而有机会离线解密（对本机本用户威胁模型不够强）。

3) **Windows 文件权限不可控**  
当前仅在非 Windows 上 `chmod 600`；Windows 下 ACL 依赖系统默认行为，无法保证“仅当前用户可读”。

4) **错误处理偏“吞错”**  
加解密失败时返回空字符串/None，可能造成“静默失效”，用户表面看不到原因（需要结合 UI 提示与日志策略）。

5) **路径与 portable 模式的对齐**  
`SecureKeyManager` 的路径规则与 `Config`（支持 `ANE_PORTABLE`）不一致；portable 期望配置与数据可随包移动时，这会造成密钥落在系统目录。

## 本次改动（作为审计结论的最小安全增强）

- 增强 key store 的 **健壮性**：
  - 读取失败时不再直接异常中断，记录 warning 并以空 store 继续（避免单个坏文件导致“无法再保存”）。
  - 写入采用 **原子写**（临时文件写完 `fsync` 后 replace），降低断电/崩溃导致的 JSON 损坏概率。
- 保持加密/密钥派生方案不变（避免破坏已存量密钥），更强的存储方案（OS keychain/DPAPI、portable 对齐、salt 演进）在后续 issue 落地。

实现位置：
- `src/core/secure_key_manager.py`

## 后续建议（供 11.1/11.2 继续落地）

- Windows 优先使用 **DPAPI**（用户上下文加密）或 `keyring`（Credential Manager）作为默认后端；否则至少引入 per-install salt + 迁移流程。
- 统一 RAG/AI 的 provider 命名（例如 `rag` / `siliconflow`），并迁移旧配置中的明文 `rag.api_key`。
- 在日志系统层做全局脱敏（`api_key` / `Authorization` / prompt/document 内容），避免“调用点忘记脱敏”。
