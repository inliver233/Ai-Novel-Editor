# REV-002 — [security][auth] dev fallback user 审计与 prod 护栏

## 背景
- 本项目提供 “dev fallback user” 机制：在开发环境（`APP_ENV=dev`）下，未登录也可用固定 `user_id` 作为当前用户，以便快速迭代 UI/接口。
- 前端会在 `/api/auth/user` 返回 401 时，尝试访问 `/api/projects` 来判断是否处于 dev fallback 模式。

## Threat model（为何需要护栏）
- **高风险误配置场景**：生产环境误以 `APP_ENV=dev` 启动（或将 prod 当 dev 配置），会导致“未登录即可访问”的 dev fallback 被开启，属于严重鉴权绕过。
- 攻击者能力假设：仅需访问公开的后端地址，无需任何凭证。
- 影响：可读取/修改项目数据（取决于路由授权），风险等级：**high**。

## 检查项
- 后端：fallback 是否严格 gated 在 `APP_ENV=dev`；是否存在“prod 误启用”的隐性入口。
- 前端：dev fallback 状态判定是否依赖后端真实鉴权语义，避免 prod 被误判。
- 文档：是否明确告知 prod 必须禁用该机制并给出可操作的配置建议。

## 发现点
1) 后端 fallback 仅在 dev 生效（实现上 gated）
- `backend/app/main.py::_ensure_local_user`：`APP_ENV != "dev"` 直接返回；仅 dev 下会创建本地用户。
- `backend/app/main.py::auth_session_middleware`：仅在 `APP_ENV == "dev"` 且无 session cookie 时才设置 `request.state.user_id` 与 `auth_source="dev_fallback"`。

2) 前端不会在 prod “误判 dev fallback”
- `frontend/src/contexts/AuthContext.tsx`：当 `/api/auth/user` 401 时，再请求 `/api/projects`：
  - 若 `/api/projects` 也失败，则状态为 `unauthenticated`
  - 只有在后端允许（dev fallback）时才会进入 `dev_fallback`

3) 主要风险来自环境变量误配置，而非代码分支条件错误
- 代码层面已按 `APP_ENV` 做了硬 gating；但如果生产部署错把 `APP_ENV` 设为 `dev`，会直接打开绕过。

## 证据（命令与关键输出摘要）
- `rg -n "auth_dev_fallback_user_id|dev_fallback|_ensure_local_user" backend/app frontend/src -S`
  - `backend/app/main.py:57 _ensure_local_user()`（含 `APP_ENV` gating）
  - `backend/app/main.py:120 fallback_user_id = ... if APP_ENV == "dev" else None`
  - `frontend/src/contexts/AuthContext.tsx:38-45`（二次请求 `/api/projects` 判定）

## 结论
- 当前实现满足“只有 dev 才启用 fallback”的预期；无需改代码即可满足本项审计目标。
- 需要补强的是 **prod 运维护栏/文档**，避免误以 `APP_ENV=dev` 启动生产服务。

## 修复方案（本次采取）
- 文档护栏（最小变更）：
  - 在 `backend/.env.example` 中补充警告：生产必须 `APP_ENV=prod`，并建议将 `AUTH_DEV_FALLBACK_USER_ID` 置空（或不设置）。
  - 在根 `README.md` 的“环境变量（后端）”补充同样提示，明确风险等级与推荐配置。

## 测试结果
- 本 issue 为审计 + 文档护栏（未改动运行逻辑），按 `Test_Method` 完成扫描与人工 review；未运行后端单测命令。
